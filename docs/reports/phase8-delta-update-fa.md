# گزارش فاز ۸ — به‌روزرسانی تفاضلی و حفظ داده

**تاریخ:** ۱۶ اکتبر ۲۰۲۶  
**مجوز:** «ادامه» پس از گزارش فاز ۷، فقط بررسی و اصلاح فاز ۸؛ بدون مجوز انتشار.  
**وضعیت پذیرش:** سخت‌سازی و آزمون کد انجام شده؛ **تأیید نهایی روی نصب کاربر باز است**.
کد `dfd6630` در CI و ساخت آزمایشی بدون انتشار موفق است؛ جزئیات و مرز شاهدها
در بخش آزمون آمده‌اند. این نتایج جای پذیرش نصب واقعی را نمی‌گیرند.

## معیار اصلی و مرز این تحویل

طبق [برنامهٔ رفع ایرادها](../plans/v1.0.6-phase-plan-fa.md)، به‌روزرسانی باید از
داخل برنامه، با اجازهٔ کاربر و فقط با بستهٔ تفاضلی انجام شود؛ پس از آن شناسهٔ
نسخه/ساخت تازه و داده‌ها دست‌نخورده باشند. این گزارش سه شاهد را جدا می‌کند:

1. آزمون کد و API جاری؛
2. مسیر مرورگر تا به‌روزرسان واقعی روی Windows آزمایشی با **کد جاری**؛
3. ارتقای واقعیِ نسخهٔ نصب‌شدهٔ کاربر، که هنوز انجام نشده است.

آزمون دوم از نسخه‌های خصوصی **99.0.0 → 99.0.1** و منبع HTTP محلی استفاده می‌کند؛
این‌ها نسخهٔ انتشار نیستند و شبیه‌سازیِ کد تاریخی ۱.۰.۶ نامیده نمی‌شوند. helper
همان سورس PowerShell محصول است، نه یک تابع mock. آزمون مستقل helper کامپایل‌شده
و بسته‌های مبدا عمومی نیز در ساخت آزمایشی زیر موفق شده است؛ آن آزمون مستقیماً
helper را فراخوانی می‌کند، نه دکمهٔ کلاینت تاریخی ۱.۰.۶.

## ایرادها و اصلاح‌های این فاز

- **اعلان آغاز برنامه:** بررسی نسخه و خواندن پیشرفت فقط نشست معتبر می‌خواهند؛
  دیگر به‌علت نداشتن sudo با ۴۰۳ متوقف نمی‌شوند. وضعیت سیستمی و پشتیبان حساس
  همچنان sudo می‌خواهند؛ دانلود/اعمال علاوه بر CSRF و sudo، محدود به مالک‌اند.
- **اجازهٔ دقیق:** درخواست دانلود نسخه و SHA-256 همان بستهٔ نمایش‌داده‌شده را
  می‌فرستد. اگر بین نمایش و تأیید، نسخه یا بسته عوض شده باشد، دانلود متوقف و
  بررسی/تأیید مجدد لازم می‌شود؛ اجازهٔ نسخهٔ اول به نسخهٔ دوم تعمیم داده نمی‌شود.
- **بدون Setup خودکار:** فقط یک delta مستقیم قابل نصب است. نبود delta، مسیر
  چندمرحله‌ای پشتیبانی‌نشده یا نسخهٔ نامعلوم، به نصب کامل خودکار تبدیل نمی‌شود؛
  پیام توقف/اقدام دستی دارد. دکمهٔ رابط نیز برای انتخاب full غیرفعال است.
- **احراز هویت مجدد:** اگر مجوز کوتاه‌عمر پیش از اعمال منقضی شود، پنجرهٔ واقعی
  ورود مجدد نمایش داده می‌شود و فقط پس از تأیید، همان درخواست یک بار تکرار می‌شود.
- **راستی‌آزمایی:** دریافت جریانی، اندازه و SHA-256، استخراج امن و پشتیبان online
  شامل WAL حفظ شده‌اند. اگر کلید امضای قابل اعتماد تنظیم شده باشد، نبود/خرابی
  امضا یا نبود فایل کلید دیگر باعث عبور بدون اعتبارسنجی نمی‌شود؛ mirror امضای
  مجاور `.sig` را می‌خواند. بدون کلید تنظیم‌شده، ادعای امضای اجباری نداریم.
- **توقف و راه‌اندازی:** به‌روزرسان PID سرویس را دریافت می‌کند و نویسندهٔ قدیمی
  را واقعاً می‌بندد؛ صرفاً CloseMainWindow نیست. محدودهٔ مسیر نصب با مرز پوشه
  تطبیق می‌شود تا نصب/برنامهٔ هم‌نام دیگری متوقف نشود. متغیرهای نسخهٔ قدیمی به
  فرزند تازه منتقل نمی‌شوند؛ stamp بستهٔ جدید مبناست.
- **موفقیت واقعی:** ساختن process به معنی موفقیت نیست؛ readiness، integrity،
  کلیدهای خارجی، توازن دفتر و شناسهٔ SPA تازه باید تأیید شوند. سپس نتیجهٔ committed
  در JSON خارج از دیتابیس ثبت می‌شود تا پس از تعویض backend نیز قابل خواندن باشد.
- **بازگردانی واقعی:** فایل‌های حذف‌شونده هم snapshot دارند؛ فایل‌های تازه هنگام
  rollback حذف می‌شوند. بازگردانی هر فایل با هش و سپس سلامت برنامهٔ قبلی بررسی
  می‌شود. شکست بازگردانی، «بازگردانی موفق» گزارش نمی‌شود. لاگ و journal فایل‌ها
  نگه داشته می‌شوند؛ پاک‌سازی اختیاری پس از موفقیت، دلیل بازگردانی مجدد نیست.
- **رابط و قطع موقت:** هنگام restart، قطع موقت ارتباط فوراً به ادعای rollback
  تبدیل نمی‌شود؛ polling محدود ادامه می‌یابد. نتیجهٔ آخر پس از reload در صفحهٔ
  سیستم دیده می‌شود. پس از موفقیت، «بارگذاری رابط جدید» صفحه را واقعاً reload
  می‌کند تا JavaScript قبلی در حافظه فعال نماند.
- **شروع هم‌زمان:** launcher عادی هنگام وجود قفل تراکنش شروع نمی‌شود؛ فقط اجرای
  کنترل‌شدهٔ helper اجازهٔ restart برای بررسی سلامت دارد. قفل در finally برداشته
  می‌شود؛ فایل‌های بازیابی پس از خرابی غیرعادی باید بررسی شوند، نه کورکورانه حذف.

## شواهد آزمون

- **۲۹۴ تست بک‌اند موفق**؛ شش مورد تازه برای discovery بدون sudo ولی با ورود،
  حفظ حفاظت پشتیبان، تغییر نسخه/هش/full پس از اجازه، نتیجهٔ پایدار پس از restart
  و رد fallback خودکار. تست امضای تنظیم‌شده نیز سخت‌گیرانه اصلاح شد.
- **۱۴۵ تست فرانت‌اند در ۲۲ فایل موفق**؛ بستهٔ دقیق تأییدشده، قطع و وصل restart،
  منع Setup و پنجرهٔ واقعی sudo با تأیید کاربر و تکرار محدود بررسی شدند.
- **۵ سناریوی کامل مرورگر محلی موفق**؛ منوهای روشن/تیره، داشبورد، گردش فاز ۷،
  قیمت‌گذاری اکسل و پیشرفت آپدیت قبلی دوباره بررسی شدند. سناریوی قدیمی آپدیت
  پاسخ‌های HTTP را mock می‌کند و به‌تنهایی شاهد نصب نیست.
- Ruff، mypy روی ۸۰ فایل، Bandit، TypeScript، ESLint، Prettier، build و تطابق
  OpenAPI/تایپ‌ها محلی موفق‌اند. هشدار قبلی حجم chunk همچنان وجود دارد.
- آزمون جدید ویندوز در `scripts/update_native_smoke.py` و
  `scripts/audit_in_app_update.cjs`، مرورگر واقعی → ورود → sudo → انصراف بدون
  دانلود → تأیید → ZIP واقعی → بررسی → پشتیبان → helper سورس → restart را اجرا
  می‌کند. منبع محلی تعداد درخواست‌ها را می‌شمارد: **یک delta و صفر Setup**.
- دیتابیس آزمون ویندوز دارای سند قطعی با کسر چهاررقمی، سفارش و تولید تمام‌شده،
  گردش موجودی و دادهٔ sentinel است؛ هش کل SQLite و فایل رسید پیش و پس از هر مسیر
  مقایسه می‌شود. سناریوی شکست با کد جدیدِ عمداً غیرقابل اجرا، پس از تغییر واقعی
  فایل‌ها شکست سلامت ایجاد می‌کند، نه صرفاً خطا پیش از شروع نصب.

### نتیجهٔ نهایی CI و ساخت آزمایشی

- [CI کد `dfd6630`](https://github.com/Houman-Amiri/VIRA-Accounting-App/actions/runs/38907169532):
  هر **۵ job موفق**؛ شامل هر دو مسیر واقعی موفقیت و بازگردانی ویندوز، با حفظ
  هش SQLite و رسید، سند قطعی و وضعیت سفارش/تولید. دانلود یک delta و صفر Setup.
- [ساخت آزمایشی بدون انتشار](https://github.com/Houman-Amiri/VIRA-Accounting-App/actions/runs/38907169650):
  هر **۶ job موفق**؛ ساخت Inno، تولید delta مستقیم از مبداهای عمومی ۱.۰.۶، ۱.۰.۷
  و ۱.۰.۸، اعتبارسنجی ZIPها و smoke نصب/ارتقا/بازگردانی با helper کامپایل‌شده.
  مرحلهٔ **Publish GitHub Release اجرا نشده**؛ هیچ تگی ساخته یا جابه‌جا نشده است.
- خطای نهایی harness ویندوز از بازماندن اتصال SQLite آزمایشی در teardown بود؛
  context اتصال صرفاً تراکنش را می‌بست، نه خود اتصال را. اتصال‌ها صریحاً بسته و
  خروج process آزمایشی انتظار کشیده می‌شود. آزمون یا خطای پاک‌سازی نادیده گرفته
  نشده؛ هر دو اجرای نهایی کامل و موفق‌اند.

## مانع مستقل نسخهٔ ۱.۰.۶

آخرین نصب تأییدشده در گفتگو ۱.۰.۶ است؛ انتشار ۱.۰.۹ به معنی نصب شدن آن روی سیستم
شما نیست. بررسی سورس تگ ثابت `v1.0.6` نشان می‌دهد دانلود، ZIP را در staging
می‌گذارد اما آن را به `update.json` و payload قابل اعمال استخراج نمی‌کند. پس
نصب جاریِ اصلاح‌شده را نمی‌توان به‌جای آن کلاینت تاریخی آزمود و نتیجه را به همهٔ
نصب‌های ۱.۰.۶ تعمیم داد. راهنمای bootstrap تفاضلی قبلی نیز معادل مسیر کاملاً
درون‌برنامه‌ای نیست.

منبع بررسی: [سورس ثابت سرویس آپدیت ۱.۰.۶](https://github.com/Houman-Amiri/VIRA-Accounting-App/blob/v1.0.6/backend/app/services/update.py).
هش SHA-256 متن آن فایل در بررسی:
`0bda75bb3c2b32ed1d5d577b81c25a1da0671c55b3f756940d833e399851a338`.
این شاهد تحلیل کد است، نه ادعای دسترسی یا اجرای نصب کاربر.

برای بستن معیار اصلی، ابتدا نسخه/کامیت واقعی نصب باید مشخص شود؛ سپس مسیر
مجاز همان مبدا، با رضایت شما و ثبت داده‌های قبل/بعد، اجرا شود. **دستور حذف نصب،
حذف دیتابیس یا دانلود خودکار Setup در این فاز داده نشده است.**

## حفظ داده، باقی‌مانده‌ها و توقف

- هیچ migration تازه یا بازنویسی دادهٔ نصب کاربر نداریم؛ نسخهٔ پروژه همچنان
  **۱.۰.۹** است و تگ عمومی قبلی تغییر نکرده. دیتابیس‌های آزمون کاملاً مجزا هستند.
- این آزمونِ بدون migration، مجوز ادعای حفظ بایت‌به‌بایتِ دیتابیس در هر migration
  آینده نیست؛ هر تغییر schema باید آزمون ارتقا/بازیابی جداگانه داشته باشد.
- تست سورس Windows و smoke مستقل helper کامپایل‌شده، دو شاهد جدا هستند.
  هیچ‌کدام اثبات ارتقا با دکمهٔ کلاینت تاریخی ۱.۰.۶، انتشار بستهٔ تازه، قطع برق در
  وسط تراکنش یا پذیرش روی دستگاه واقعی نیستند؛ این موارد هنوز تأیید نشده‌اند.
- فاز ۴-ب، تأیید قیمت روی نصب و popup واقعی Windows همچنان مستقل و بازند.
- **انتشار جدید مجاز/انجام نشده؛ فاز ۸ از نظر پذیرش نصب بسته نمی‌شود.** پس از
  ارائهٔ گزارش و پیش‌نمایش، برای تأیید نسخهٔ نصب و تصمیم بعدی توقف می‌کنیم.
