# گزارش پیش‌انتشار نامزد ۱.۰.۱۰ — مبدا واقعی ۱.۰.۹

**تاریخ:** ۱۶ اکتبر ۲۰۲۶  
**دامنهٔ مجوز فعلی:** ادامهٔ آزمون پیش‌انتشار؛ نه تگ یا انتشار عمومی.  
**وضعیت:** همهٔ gateهای نامزد `f6fc50b` سبز؛ توقف برای تأیید صریح انتشار.

## مبدا تأییدشده و آنچه آزمون می‌شود

تصویر تازهٔ کاربر، نصب **۱.۰.۹ / `7d78720`** و برابری سه شناسهٔ نصب، مرورگر و
کد کامپایل‌شده، با migration `0005_pricing_settings` را تأیید می‌کند. تصویر و
مسیر شخصی کاربر در مخزن کپی نشده‌اند. تأیید نسخه، تأیید همهٔ داده‌ها یا ارتقای
بعدی نیست؛ فاز ۸ تا پذیرش روی نصب واقعی باز می‌ماند.

آزمون تازه، برخلاف fixture خصوصی 99.0.x، بستهٔ عمومی واقعی زیر را مبدا می‌گیرد:

- [بستهٔ نصب‌چیدمان عمومی ۱.۰.۹](https://github.com/Houman-Amiri/VIRA-Accounting-App/releases/download/v1.0.9/vira-v1.0.9-app.zip)
- اندازهٔ ثبت‌شده در GitHub: `201547373` بایت؛
- SHA-256 ثابت asset، دریافت‌شده از API انتشار GitHub:
  `5b5ddba7656a35c7ab14d2f92d0d0263f442f1d1890d4ba74e1d27e632928e16`.

هش ZIP و سپس بایت‌های فایل‌های manifest پیش از شروع بررسی می‌شوند. کد backend،
بسته‌های Python، launcher و JavaScript تاریخی بازسازی یا با کد امروز جایگزین
نمی‌شوند؛ bootstrap تزریقی و mock helper در این مسیر وجود ندارد.

## تغییرهای این مرحله

- metadata پروژه و lockfile برای **نامزد آزمایشی ۱.۰.۱۰** هم‌راستا شدند؛ تگ و
  انتشار عمومی همچنان ساخته نشده‌اند. فرمول اکسل یا migration تازه نداریم.
- کلاینت ۱.۰.۹ helper جدید را از payload اجرا می‌کند، اما آرگومان جدید ResultPath
  را نمی‌فرستد. helper فقط در الگوی شناخته‌شدهٔ
  `updates/<version>/<uuid>/payload` مسیر نتیجه را بازیابی می‌کند تا backend تازه
  پس از restart نتیجهٔ واقعی را بخواند. آرگومان صریح کلاینت تازه اولویت دارد.
- gate مستقل در workflow ساخت، کلاینت عمومی ۱.۰.۹ را از مرورگر تا helper
  **کامپایل‌شده** می‌آزماید؛ اجرای مستقیم helper به‌جای فشردن دکمهٔ اپ نیست.
- سه delta مستقیم از ۱.۰.۷، ۱.۰.۸ و ۱.۰.۹ باید وجود داشته باشند، معتبر باشند و در
  smoke نصب/ارتقای ویندوز اجرا شوند. فقدان مبدا ۱.۰.۹ مجاز به skip نیست.
- آزمون واقعی روی نامزد `9c99c23` اعمال، سلامت و حفظ هش داده‌ها را گذراند، اما
  دکمهٔ پایان ظاهر نشد: manager تازه پیش از ثبت نتیجه، idle می‌داد و کلاینت قدیمی
  پایش را قطع می‌کرد. تست رگرسیون همین حالت ابتدا واقعاً شکست خورد؛ اکنون تا
  نتیجهٔ متعلق به همان قفل (nonce تلاش و PID helper)، وضعیت applying حفظ می‌شود.
  نتیجهٔ قدیمی یا PID بازیافت‌شده، موفقیتِ تلاش تازه محسوب نمی‌شود. assertion
  دکمهٔ پایان حذف نشده است؛ تکرار آزمون با همین assertion در نامزد `f6fc50b` موفق شد.
- کنترل فایل‌های مبدا/مقصد پس از اجرا، فقط cache قابل بازتولید Python را مستثنا
  می‌کند؛ فایل‌های برنامه و metadata همچنان باید با هش بسته تطبیق داشته باشند.

## مسیر و کنترل‌های آزمون جدید

فقط روی Windows GitHub Actions مجزا، در مسیر دارای فاصله و با پروفایل، دیتابیس و
رسید آزمایشی خارج از پوشهٔ نصب:

1. اجرای launcher عمومی، ورود مالک و sudo؛ بررسی نسخه و سه شناسهٔ `7d78720`؛
2. «بررسی به‌روزرسانی»، نمایش نسخهٔ ۱.۰.۱۰ و انصراف: صفر دانلود؛
3. تأیید و دریافت ZIP واقعی، استخراج/راستی‌آزمایی و ایجاد پشتیبان؛
4. اعمال از دکمهٔ واقعی، restart، بررسی سلامت و نتیجهٔ helper؛
5. بررسی هش کل SQLite و رسید؛ سند قطعی چهاررقمی، سفارش و تولید تکمیل‌شده، موجودی؛
6. تازه‌سازی رابط و بررسی برابری سه شناسهٔ ساخت مقصد؛ یک delta و صفر Setup؛
7. مسیر مستقل شکست با مقصدِ خصوصیِ عمداً غیرقابل اجرا؛ بررسی بازگردانی، سلامت و
   هش فایل‌های قبلی و داده‌ها. ZIP خراب جایگزین ZIP نامزد نمی‌شود.

هش SQLite بلافاصله پیش از apply، پس از sudo، با وضعیت پس از سلامت/نتیجهٔ helper و
**پیش از sudo نهایی** مقایسه می‌شود. ورود مجدد نهایی برای خواندن اطلاعات سامانه
می‌تواند audit امنیتی بنویسد؛ ادعای یکسان‌ماندن بایتی DB در تمام جلسه نداریم.

داده‌ها واقعی از نظر schema و گردش ثبت هستند، اما کاملاً آزمایشی‌اند. دادهٔ نصب
کاربر خوانده یا تغییر داده نشده است. پشتیبان آزمون نیز در همان پروفایل مجزا است.

## تفاوت‌های نخستین ارتقا با کلاینت اصلاح‌شده

تحلیل کد تاریخی نشان می‌دهد دکمهٔ پایان ۱.۰.۹ فقط پنجره را می‌بندد؛ بنابراین
تازه‌سازی صریح صفحه در نخستین ارتقا آزموده شد و به کاربر گفته می‌شود. تغییر helper
نمی‌تواند JavaScript از قبل بارگذاری‌شدهٔ کلاینت قدیمی را به گذشته برگرداند.

در قطع موقت ارتباط، رابط قدیمی ممکن است پیام خطای موقت نشان دهد؛ این پیام به معنی
نتیجهٔ نهایی helper نیست. پل وضعیت تازه، پایش را تا نتیجهٔ همان تلاش حفظ می‌کند.

API قدیمی ۱.۰.۹ نیز نتیجهٔ پایدار rollback را نمی‌خواند. در سناریوی بازگردانی،
آزمون فایل واقعی نتیجهٔ helper، سلامت، نسخه و هش‌ها را مستقل بررسی می‌کند؛ پیام
عمومی خطای کلاینت قدیمی را به‌جای اعلان اختصاصیِ بازگردانی موفق جا نمی‌زند.
در کلاینت جدید، دکمهٔ بارگذاری رابط و نمایش نتیجهٔ پایدار افزوده شده‌اند.

### خطاهای آشکارشده؛ بدون حذف آزمون

- تفاوت absolute/rooted بودن مسیر در Windows، یک تست منفی را شکست داد؛ تشخیص
  anchor و مسیر drive-relative اصلاح و تست‌های ویندوز گسترش داده شدند.
- تغییر LOCALAPPDATA برای جداسازی نصب، cache مرورگر Playwright را نیز جابه‌جا
  می‌کرد؛ cache آن صریحاً از پروفایل محصول جدا شد. مرورگر پیش‌فرضِ بازشده توسط
  launcher واقعی و cmdهای آزمایشی نیز باید پیش از حذف پوشه بسته شوند.
- یک اجرای ساخت در مرحلهٔ کامپایل helper شکست خورد؛ لاگ کامل در محیط قابل دریافت
  نبود و annotation فقط exit code داشت. تشخیص محدود و مستقل compiler افزوده شد؛
  در اجرای بعدی مرحلهٔ کامپایل عبور کرد. علت قطعی اجرای قبلی ادعا نمی‌شود.

## مرز انتشار و پذیرش

این گزارش نه مجوز انتشار است، نه تأیید ارتقای دستگاه کاربر. اکنون gateهای نامزد
نهایی شده‌اند و برای تأیید صریح یادداشت‌های فارسی و انتشار توقف می‌کنیم. در صورت
مجوز بعدی نیز، تگ باید تازه و ثابت باشد و بستهٔ همان ساخت نهایی دوباره آزموده شود.

فاز ۴-ب، تأیید قیمت تعداد ۱ و ۱۰، popup بومی Windows و PDF بومی/Word مستقل‌اند.
پیش‌نمایش پورت ۵۱۷۳ فقط دادهٔ آزمایشی دارد؛ آخرین انتشار عمومی همچنان ۱.۰.۹ است.
