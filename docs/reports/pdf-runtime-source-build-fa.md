# گزارش اثبات فنی runtime بومی PDF با منشأ سورس مشخص

تاریخ: ۲۰۲۶-۱۰-۱۷ — **ساخت و آزمون فنی موفق؛ مجوز توزیع و نصب عمومی هنوز تأیید نشده‌اند.**

## نتیجهٔ اصلی

به‌جای تأیید ضمنیِ ۲۷ DLL ناشناختهٔ SDK قبلی، یک نامزد **جداگانه** از منابع
پین‌شده ساخته شد. ساخت واقعی ویندوز، گردآوری سورس/مجوزها و آزمون PDF با Python
واقعاً بسته‌بندی‌شده موفق شدند. مجموعهٔ جدید **۲۱ DLL / ۱۴٬۴۱۷٬۴۰۸ بایت** دارد؛
هر ۲۱ فایل هنگام آزمون از مسیر همین نامزد بارگذاری شدند.

این نتیجه نه ۲۷ DLL قبلی را تأیید می‌کند، نه گیت حقوقی را می‌بندد و نه به معنی
افزوده‌شدن موتور بومی به نسخهٔ نصب‌شدهٔ کاربر است. وضعیت نامزد جدید همچنان:

`BLOCKED_PENDING_LICENSE_AND_CORRESPONDING_SOURCE_REVIEW`

## سازوکار ساخت و حفاظت‌ها

- manifest/triplet مستقل در `native/pdf-source/`؛ `VCPKG_BINARY_SOURCES=clear` و
  `--binarysource=clear` مانع بازیابی بسته‌های آمادهٔ native می‌شوند. کامپایلر، SDK
  و executableهای bootstrap/build-tool پیش‌نیازند؛ ادعا نمی‌شود خود آن‌ها از سورس
  ساخته شده‌اند. این گیت traceability است، نه SDK آفلاین یا reproducibility کامل.
- target: DLL قابل‌تعویض، CRT استاتیک، release-only. host: CRT پویا و release-only؛
  ابزارها و DLLهای host وارد نامزد runtime نمی‌شوند. این تفکیک در آزمون‌ها کنترل می‌شود.
- مالک DLL از receipt نصب استخراج می‌شود. import ناشناخته شکست است؛ نسخهٔ PE یا
  حضور اتفاقی کتابخانه در PATH/System32 به معنی تأیید source/licensing نیست.
- سورس کامل وصله‌شدهٔ بسته‌های target، شامل وابستگی‌های استاتیک و بسته‌های اضافی
  ساخته‌شده، به‌همراه recipe/patchهای vcpkg و wrapper/workflow واقعی ضبط می‌شود.
  نبود سورس برای کتابخانه/header native یا نبود copyright/SPDX شکست است.
- symlink نسبیِ داخل همان بسته به‌صورت Unix symlink در ZIP حفظ و جداگانه فهرست
  می‌شود؛ مقصدش خوانده نمی‌شود. لینک مطلق یا خارج‌شونده رد می‌شود. fixtureهای
  dangling/cyclic داخلی قابل ثبت‌اند، بدون دنبال‌کردن لینک یا خواندن فایل بیرونی.
- هش درخت: مسیر POSIX مرتب‌شدهٔ case-sensitive، نوع `file`/`symlink` و SHA256 محتوا؛
  برای لینک، محتوا نام نسبیِ مقصد است. بازبین مستقل این درخت‌ها را از ZIP بازسازی
  و مقایسه کرد، بدون استخراج ناامن یا اجرای DLL.
- متن مجوز در JSON صرفاً preview است؛ بایت‌های اصلی و هش آن‌ها در آرشیو محفوظ‌اند.
  در این اجرا همهٔ previewها UTF-8 lossless بودند. وجود متن مجوز یا SPDX به معنی
  پذیرش انتخاب مجوز، کفایت notices یا اجازهٔ توزیع نیست.
- وجود یک بستهٔ ساخته‌شده در inventory به معنی استفاده از DLL آن در runtime نیست؛
  `selected_dlls` این تمایز را نشان می‌دهد. مثلاً Cairo/Pixman/PThreads ساخته و
  سورسشان ضبط شده، ولی DLLهایشان جزو closure انتخابی نیستند.

## گیت‌های باز — این گزارش آن‌ها را نمی‌بندد

۱. **مجوز توزیع:** انتخاب مجوزهای dual-license، notices/اعتباردهی لازم، حقوق
   recipeهای اختصاصی، شروط compiler/CRT و تحویل پایدار corresponding source باید
   بازبینی شوند. حتی `libiconv` در metadata پورت license صریح ندارد؛ متن copyright
   و سورسش موجود است، اما این فقدان با حدس یا تأیید خودکار پوشانده نشده است.
۲. **bootstrap عمومی و Unicode:** worker همچنان از تنظیمات موقت ASCII برای
   Fontconfig استفاده می‌کند. مسیر برنامه/Python/DLL/fonts فارسی و فاصله‌دار است،
   اما پیکربندی مستقلِ همهٔ مسیرهای Unicode در نصب عمومی هنوز اثبات نشده است.
۳. **نصب و به‌روزرسانی native:** ورود runtime تأییدشده به manifest عادی، راه‌انداز،
   delta و rollback آن و تأیید حداقل نسخهٔ Windows هنوز انجام نشده است. باینری کامپایلر/ابزارهای میزبان stage نشده‌اند
   و هیچ runtime خودکار جدیدی به launcher متصل نشده است.
۴. **پذیرش نهایی نصب‌شده:** چاپ/RTL/داده‌های مالی و سناریوهای واقعی کاربر طبق خواست
   او پس از اتمام فازها آزموده می‌شوند؛ از نبود دادهٔ دستی، موفقیت مالی استنباط نشده است.

**جمع‌بندی:** اثبات فنیِ «ساخت از سورس قابل‌ردیابی + مواد سورس/مجوز + PDF واقعی با
Python همراه» موفق است. نامزد هنوز `DO_NOT_DISTRIBUTE` است؛ نسخه، تگ، release،
مجوز انتشار و پذیرش نهایی کاربر ایجاد نشده‌اند.
