# گام تکمیلی PDF بومی و وزیرمتن — بدون انتشار

تاریخ: ۲۰۲۶-۱۰-۱۷

## مرز این گام

پس از اتمام گیت خودکار اطلاعات پایه و دستور «ادامه بده»، این گام برای رفع ابهام
«HTML چاپی یا PDF واقعی؟» شروع شد. هیچ DB شخصی، مبلغ، فرمول، migration، نسخه یا تگ
عمومی تغییر نمی‌کند. داده‌های آزمون ساختگی هستند؛ رشتهٔ شامل هر ۳۰ رقم در بخش
جمع کل، عمداً **کاوش فونت** است، نه مبلغ واقعی یا تأیید محاسبات مالی.

**نتیجهٔ قطعی این گام:** رندر واقعی Windows، تست API احرازشده و **هر پنج job CI موفق‌اند**.
گیت خودکار رندر و embedding بسته شد؛ **گیت بسته‌بندی runtime و پذیرش نصب نهایی هنوز باز است**.

## تغییرات

- HTML چاپیِ fallback اکنون هر دو فایل اصلی وزیرمتن را به‌صورت `data:font/ttf;base64`
  همراه دارد. مسیر نسبی پیشین برای مرورگری که سند را از مسیر API باز می‌کرد معتبر
  نبود؛ چاپ جایگزین اکنون وابسته به فونت سیستم یا دانلود اینترنتی نیست.
  CSP همین پاسخ، `font-src data:` را مجاز می‌کند؛ پیش‌فرض منابع و اسکریپت‌ها
  همچنان `none` است. سیاست امنیتی عمومی SPA شل نشده است.
- PDF از همان TTFهای همراه اپ و پیکربندی صریح FontConfiguration استفاده می‌کند.
  دریافت منبع فقط برای URI دقیق همان دو فایل مجاز است؛ HTTP، فایل دیگر و URL
  دلخواه به fetcher واقعی نمی‌رسند. متن مشتری همچنان با Jinja escape می‌شود.
- رفتار API عوض نشده: PDF موفق `application/pdf` و فایل `.pdf`؛ نبود runtime بومی
  همچنان HTML با `text/html` و نام `.html` می‌دهد. HTML هرگز در گیت بومی پذیرفته نیست.
- آزمون مستقل `scripts/pdf_native_smoke.py` سند کوتاه و ۱۰۰ ردیفی می‌سازد؛ فایل PDF
  را می‌خواند و A4، چندصفحه‌ای شدن، فونت‌های **واقعاً استفاده‌شده در عملگرهای متن**،
  TTF تعبیه‌شده و خانواده/وزن واقعی آن‌ها و نگاشت Unicode ارقام مصرف‌شده را بررسی می‌کند.
  نام CSS، نام فونت PDF یا وجود صرف ToUnicode برای قبولی کافی نیست.
- هر ۳۰ رقم لاتین، فارسی و عربی در هر دو وزن ۴۰۰ و ۷۰۰ آزموده می‌شوند. آزمون API
  احرازشده نیز با پرچم سخت‌گیرانه باید PDF واقعی با ارقام مبلغ نمونه تولید کند.
- کنترل‌های منفی، HTML، کاغذ نادرست، فونت جایگزین، فونت تعبیه‌نشده، Unicode مفقود،
  وزن Bold استفاده‌نشده و ارقام صرفاً موجود در cmap ولی مصرف‌نشده را رد می‌کنند.

## محیط Windows و منشأ فایل‌ها

فقط برای آزمون، آرشیو رسمی زیر دانلود و SHA256 آن پیش از استخراج بررسی می‌شود:

- upstream: `Kozea/WeasyPrint`, tag `v70.0`
- asset: `weasyprint-windows-onedir.zip`
- SHA256: `ab1151f210b4e6bb7aa7a79e91a67e8ddb760094c107bfda55241b6aaefe7d53`

اپ از مسیری شامل فاصله و حروف فارسی اجرا می‌شود. Fontconfig به پوشهٔ فونت خالی و
cache موقت محدود است؛ وزیرمتن باید از `@font-face` بیاید، نه نصب در Windows.
بعد از رندر، مسیر DLLهای Pango، PangoFT2، GObject، HarfBuzz و Fontconfig که واقعاً
در پردازش بارگذاری شده‌اند کنترل می‌شود تا از همان fixture باشند، نه GTK/MSYS
از پیش نصب‌شده. فقط PDFهای ساختگی و JSON اثبات در artifact قرار می‌گیرند، نه DLLها.
وابستگی بازرسی `pypdf` فقط dev است و به بستهٔ تولید افزوده نشده است.

## شواهد

- محلی: **۳۶۸ تست بک‌اند موفق**، شامل ۱۱ تست جدید؛ ۱۵ تست هدفمند PDF/تایپوگرافی موفق.
- یک آزمون جدید مرورگر واقعی برای HTML چاپی موفق است: هر دو FontFace بارگذاری شدند،
  DevTools فونت واقعی متن/ارقام را `Vazirmatn-Regular` و `Vazirmatn-Bold` با
  `isCustomFont=true` گزارش کرد؛ صفر درخواست منبع خارجی و صفر نقض CSP.
- اجرای نخست CI روی `2548d2d` چهار job موفق داشت، اما تست منفی مسیر فایل روی Windows
  به علت ساخت URI از مسیر بدون drive شکست خورد؛ مسیر آزمون به absolute path مستقل
  از سیستم‌عامل اصلاح شد. این شکست پنهان یا به‌عنوان قبولی بومی گزارش نشده است.
- **۱۹۶ تست فرانت‌اند** و **۶ سناریوی کامل مرورگر واقعی** روی DB تازهٔ ساختگی موفق‌اند.
  TypeScript، ESLint، Prettier، Ruff، Bandit و Mypy برای ۸۴ فایل موفق‌اند.
- شکل داده/endpoint قرارداد API عوض نشده است؛ تنها توضیح پیش‌نیاز PDF از Pango/Cairo
  به Pango/Fontconfig/HarfBuzz تصحیح و OpenAPI و types بازتولید شده‌اند. گیت قرارداد
  در اجرای `691ae7b` همین drift توضیح را گرفت؛ نتیجهٔ نهایی باید با فایل بازتولیدشده باشد.
- export واقعی وابستگی تولید بررسی شد: `pypdf` در آن نیست؛ WeasyPrint همچنان ۷۰٫۰ است.
- در اجرای `c3ab191`، رندر مستقل Windows واقعاً موفق شد: سند کوتاه ۱ صفحه/۲۱٬۴۶۳ بایت
  و سند بلند ۴ صفحه/۳۲٬۹۷۳ بایت، ۳۰ رقم در هر دو وزن؛ مسیر DLLها از fixture تأیید شد.
  اما انتظار اولیهٔ API اشتباهاً رقم‌های «قیمت واحد» را در وزن Bold جمع کل نیز می‌خواست.
  برای سفارش دو عددی، جمع **۵٬۵۲۱٬۴۹۷** است، نه ۲٬۷۶۰٬۷۴۸٫۵. انتظار بر اساس هر وزن
  اصلاح شد؛ فرمول/مبلغ/قالب‌بندی واقعی عوض نشده و گیت همهٔ ۳۰ رقم دست‌نخورده است.
- بازرسی منابع با API جدید `URLFetcher` در WeasyPrint قفل‌شدهٔ ۷۰ هماهنگ شد؛ حداقل
  وابستگی به همان ۷۰ تنظیم شده است، نه اینکه موتور قفل‌شده ارتقا داده شده باشد.
- رندر بومی در sandbox محلی به علت نبود Pango اجرا نشده است؛ HTML یا mock به جای
  آن گزارش نشده است. نتیجهٔ Windows از اجرای نهایی و annotation ساخت‌یافتهٔ آن استخراج شد.

SHA256 سند کوتاه:
`ae92659254d59fed845c8ce4880d7bfa2846d64850085e5facfc657579ee4ebd`

SHA256 سند بلند:
`8273a9acad1e600661ec44a7ff4d2d1ae6e8fba69914a5b1c2aa0344871c5650`

هر پنج job نهایی، از جمله قرارداد بازتولیدشده، موفق‌اند. در Windows علاوه بر گیت PDF،
آزمون واقعی delta/rollback و مهاجرت از مبدا عمومیِ دست‌نخوردهٔ ۱.۰.۱۰ با بازیابی
schema/data توسط helper کامپایل‌شده نیز موفق شدند. این نتایج جای آزمون نصب/PDF با
runtime همراه را نمی‌گیرند، چون fixture بومی خارج از payload نصب است.

## موارد باز — نباید با این گیت بسته اعلام شوند

1. **runtime بومی هنوز در payload نصب/دلتا بسته‌بندی نشده است.** fixture رسمی صرفاً
   برای اثبات رندر در CI است و وارد `stage_app_payload.ps1` نشده است. انتخاب closure
   DLLها، مجوزها/اعلان‌های third-party و دسترسی به corresponding source باید پیش از
   توزیع باینری حل شود. نصب سراسری GTK روی سیستم کاربر راه‌حل تحمیلی نیست.
2. آزمون مستقل با Python و وابستگی‌های محیط توسعه اجرا می‌شود، نه نصب نهایی با
   CPython همراه؛ پذیرش نصب نهایی/آپدیت runtime گیت جداگانه لازم دارد.
3. بازبینی انسانی راست‌به‌چپ، صفحه‌بندی و چاپ روی Windows نصب‌شده و پذیرش کسب‌وکاری
   با دادهٔ واقعی طبق خواست کاربر در انتهای کار باقی است؛ صحت نگاشت و embedding
   به‌تنهایی تأیید تصویری یا تأیید مبلغ نیست.
4. هیچ نسخه، نصب‌کننده، تگ، انتشار عمومی یا خروجی مستقل Word ساخته نشده است.
