# ۴-ب/۳-الف — پیش‌نیاز ایمنی مهاجرت اطلاعات پایه

**تاریخ:** ۲۰۲۶-۱۰-۱۷
**وضعیت:** زیرساخت ایمنی و تمرین revision واقعی موفق؛ هر پنج job CI، شامل گیت
ویندوز با نسخهٔ عمومی ۱.۰.۱۰ و helper کامپایل‌شده، موفق شدند.
**این گزارش، تکمیل منوی نوع/واحد/تأمین‌کننده نیست.**

## دلیل این گام

در بررسی پیش‌نیاز مهاجرت مشخص شد helper قبلی، فایل‌های برنامه را بازمی‌گرداند ولی
بک‌آپ دیتابیس را هنگام rollback برنمی‌گرداند. اگر مقصد به revision جدید رسیده باشد،
Alembic نسخهٔ قبلی ممکن است آن revision را نشناسد و برنامه بالا نیاید. داشتن بک‌آپ
پیش از update، بدون مسیر بازگردانیِ آزموده، این مشکل را حل نمی‌کرد.

پیش از تغییر CHECKهای نوع/واحد و ثبت مدل‌های مرجع، همین شکاف ایمنی بررسی شد.

## تغییرات اجرایی

- helper پس از توقف نویسنده‌های برنامه و پیش از تغییر فایل‌ها، snapshot مستقل
  مربوط به **همان تلاش** را با SQLite backup API می‌سازد. مسیر DB از تنظیم واقعی
  کلاینت جاری می‌آید؛ برای کلاینت عمومی قدیمی، با config همان نصب و محیط launcher
  بازیابی می‌شود. DB پیش‌فرضِ حدسی یا «آخرین بک‌آپ موجود» انتخاب نمی‌شود.
- ابزار stdlib در بیرون پوشهٔ برنامه، داخل delta و همراه SHA-256 ارسال می‌شود؛
  هم کل بسته و هم عضو ابزار بررسی می‌شوند. در rollback به نسخه‌ای که این فایل را
  ندارد نیز ابزار بیرونی باقی می‌ماند. Python قبلی پس از بازیابی فایل‌ها استفاده می‌شود.
- snapshot با سلامت، FK، revision، hash فایل و fingerprint کامل schema/داده بررسی
  می‌شود. fingerprint شامل تعریف جدول/trigger و همهٔ داده‌ها، از جمله INTEGERهای
  مقیاس‌دار، شناسه‌ها و تاریخچه است؛ نوسان شمارنده‌های فیزیکی WAL، دادهٔ تجاری نیست.
- در شکست، ابتدا مقصد متوقف و فایل‌های قبلی برگردانده می‌شوند؛ سپس DB همان تلاش
  بررسی و در صورت تغییر، با snapshot تأییدشده جایگزین می‌شود. DB شکست‌خورده و
  فایل‌های WAL/SHM/journal آن در quarantine نگه داشته می‌شوند، نه اینکه حذف شوند.
- اگر محتوای DB اصلاً تغییر نکرده باشد، بازگردانی آن را بی‌دلیل بازنویسی نمی‌کند؛
  شرط قدیمی برابری hash فیزیکی برای updateهای بدون تغییر schema حفظ می‌شود.
- پیش از اعلام rollback موفق، schema/data و سلامت برنامهٔ قبلی باید تأیید شوند.
  snapshot خراب یا بازیابی ناموفق، موفقیت جعلی اعلام نمی‌کند.
- در کد جاری، تا پایان بررسی updater و برداشته‌شدن lock، درخواست‌های نویسنده با
  ۵۰۳ و `Retry-After` متوقف‌اند؛ GET سلامت/وضعیت فعال می‌ماند. jobهای دوره‌ای نیز
  تا پایان lock نمی‌نویسند. بنابراین ثبت جدیدی در مقصدِ تأییدنشده پذیرفته نمی‌شود
  که بعداً هنگام rollback از دست برود.

## آزمون‌ها

- RED نخست: پنج تست ابزار DB به دلیل نبود پیاده‌سازی شکست خوردند؛ سپس سبز شدند.
- محلی: **۳۳۵ تست بک‌اند** و **۱۸۶ تست فرانت‌اند** موفق شدند؛ Ruff و mypy نیز موفق.
- نه تست تازهٔ DB/lock شامل تغییر schema و revision، مقادیر دقیق، نگهداری DB
  شکست‌خورده، snapshot دادهٔ WAL، عدم بازنویسی DB یکسان، snapshot خراب، DB ناموجود،
  schema واقعی جاری، جلوگیری از ثبت HTTP، توقف/ادامهٔ job دوره‌ای و اجرای ابزار
  آزمون از دایرکتوری غیرریشهٔ مخزن هستند.
- تست CLI ساخت delta، حضور ابزار مستقل و hash آن را بررسی می‌کند.

### گیت Windows و نسخهٔ عمومی

کد نخست این گام `31870ee` است. CI نخست `38985504489` در سناریوی Native،
پیش از apply، به‌دلیل مسیر import ابزار checkpoint شکست خورد؛ چهار job دیگر سبز بودند.
این خطای fixture اصلاح و regression test اجرای script از دایرکتوری دیگر اضافه شد؛
تست دور زده یا امنیت کم نشد. لاگ خطای مرورگر نیز cookie/tokenهای fixture را redact می‌کند.
کد اصلاح‌شده `1a3bdf5` و
[CI تازه](https://github.com/Houman-Amiri/VIRA-Accounting-App/actions/runs/38985887353)
با SHA برابر `1a3bdf582832c4ec58006da524d02abfce00d87a`: **هر پنج job موفق**.
در Windows، هم سناریوهای موجودِ موفقیت/شکست روی fixture کد جاری و هم مرحلهٔ
«Public 1.0.10 real schema migration and compiled-helper database rollback» موفق شدند.
workflow انتشار skipped بود؛ تغییرات مستندات پس از این شاهد، کد اجرایی را عوض نمی‌کنند.

گیت افزوده‌شده، روی runner ایزوله، فایل عمومی **۱.۰.۱۰ / `5b47ebb`** را با digest
ثابت زیر دریافت و بررسی می‌کند؛ پایه بازسازی یا bootstrap آن تزریق/جایگزین نمی‌شود:

`73c36ae9a24fab4590b24f8af7343aeaab6b4c7f19c1f2cd38dd6db88e19fb97`

سناریو از رابط واقعی کلاینت عمومی، تأیید مالک و دانلود فقط delta استفاده می‌کند.
مقصد خصوصی `99.0.1`، helper کامپایل‌شدهٔ جدید و یک revision واقعی Alembic به نام
`0006_catalog_rollback_probe` دارد: جدول مرجع و FK ایجاد می‌شود، revision جدید
در DB ثبت می‌شود، و **پس از مهاجرت** مقصد عمداً شکست می‌خورد. سپس باید:

1. marker مستقل اجرای revision جدید وجود داشته باشد؛ شکست قبل از migration کافی نیست.
2. فایل‌های immutable نسخهٔ عمومی و revision `0005_pricing_settings` بازیابی شوند.
3. جدول آزمایشی از DB فعال ناپدید و fingerprint کامل داده/schema با قبل برابر شود.
4. DB شکست‌خورده با revision جدید برای بررسی محفوظ باشد.
5. سند قطعی، گردش و موجودی، سفارش تکمیل‌شده، مقادیر مالی و فایل رسید حفظ شوند؛
   سلامت/FK/توازن/شناسه‌های ساخت نسخهٔ قبلی تأیید و تعداد دریافت Setup صفر باشد.

## مرز اثبات و ادامه

revision بالا **فقط در payload آزمایشی ساخته می‌شود**؛ migration برنامه، schema
پیش‌نمایش و DB کاربر هنوز همان `0005_pricing_settings` هستند. این تمرین، سازوکار
بازگردانی را با تغییر revision واقعی می‌آزماید، ولی جای آزمون migration نهایی
اطلاعات پایه را نمی‌گیرد. وقتی migration واقعی نوع/واحد آماده شد، گیت باید با همان
تغییر واقعی نیز تکرار شود و FK/مانده‌ها/قیمت‌ها پیش و پس از آن سنجیده شوند.
در آن زمان seed مبدا نیز باید با migrationهای خود نسخهٔ عمومی ساخته شود، نه head
جدید مخزن؛ در تمرین فعلی هر دو head برابر ۰۰۰۵ هستند و startup دست‌نخوردهٔ مبدا
سازگاری آن را تأیید کرده است.

منوی اطلاعات پایه، مدل‌های مرجع پویا، حذف/غیرفعال‌سازی و اتصال فرم ثبت کالا هنوز
باقی‌اند. ثبت گزینهٔ جدید نباید خودکار نقش فیلامنت/محصول یا تبدیل واحد ایجاد کند.

هیچ تگ، نسخه یا انتشار جدیدی ساخته نشده و نصب عمومی کاربر همچنان ۱.۰.۱۰ است.
از DB نصب کاربر استفاده نشده؛ آزمون دستی طبق درخواست او تا پایان فازها معوق است.
